# ANTuRide iOS UI 设计系统主约束

> **用途**：这是 ANTuRide iOS 的项目级 UI、布局、交互与无障碍约束。新增页面、重构现有页面、添加组件或调整导航前，必须先遵循本文件。
>
> **适用范围**：`Sources/App`、`Sources/Features`、`Sources/DesignSystem`、UI 测试与页面级设计文档。
>
> **平台基线**：SwiftUI，iOS 16+，当前目标为 iPhone 竖屏与横屏；iOS 26 的 Liquid Glass 只能作为渐进增强，不能成为 iOS 16–25 的基础依赖。
>
> **产品定位**：个人车辆伴侣应用，连接 ANT BMS 与电机控制器，提供可快速扫读的驾驶仪表盘、实时电池状态、行程、续航、RPM 加速测试与本地诊断。驾驶期间优先“少看、易懂、状态可信”，复杂配置默认在停车时完成。

---

## 1. 不可违反的设计原则

1. **原生优先**：优先使用 SwiftUI 原生控件和系统行为：`NavigationStack`、`TabView`、`List`、`Form`、`Section`、`LabeledContent`、`Button`、`Toggle`、`Picker`、`Menu`、`ProgressView`、`ShareLink`、`confirmationDialog`。除非有明确产品价值，不引入第三方 UI 库或自定义控件替代系统控件。
2. **可信数据优先**：实时数据必须区分有效、过期、未连接、缺失和错误；不能用 `0`、假进度或装饰性动画掩盖未知状态。没有有效值时显示 `--`，并在附近说明原因。
3. **一眼读懂**：仪表盘只突出当前状态、速度、SOC/电压、功率、续航和行程控制；低频配置、诊断、导出和历史数据进入二级页面。
4. **可访问优先**：视觉层级不能牺牲 Dynamic Type、VoiceOver、减少动态效果、颜色对比和触控尺寸。颜色不是唯一的状态编码方式。
5. **同一语义，同一组件**：同类状态、数值、错误、空状态、导出和危险操作必须复用同一套组件与文案结构，不在页面内临时拼装视觉样式。
6. **不复制 Android 视觉**：可以保持数据、协议和业务语义一致，但 iOS 页面采用 iOS 的导航、列表、表单、返回手势、系统字体、系统色和系统反馈。
7. **渐进增强而非全屏装饰**：iOS 26 Liquid Glass 属于浮在内容之上的导航/控件层，不用于指标、图表等内容卡片；现有 `glassCard()` 在内容卡片上的 Liquid Glass 分支应随仪表盘重构重新评估，不再扩大使用范围。标准系统 Material、分组背景、模糊、渐变、阴影和动效必须克制使用，不得影响文本对比度和实时刷新性能。

## 2. 信息架构与导航约束

### 2.1 顶层 Tab

当前顶层固定为五项，顺序不可随页面增加而随意改变：

1. **仪表盘**：驾驶中最常用的实时状态和行程控制。
2. **电池**：BMS 电池包、单体、温度、MOS、均衡与通讯状态；不提供扫描连接。
3. **控制器**：控制器实时详细数据、状态与故障；记录/历史在二级页面，不提供扫描连接；提供 RPM 加速测试快捷入口（与设置入口指向同一测试页，不重复编辑配置）。
4. **行程**：本地行程列表、详情、曲线与导出。
5. **设置**：蓝牙设备（分别搜索/连接/断开/忘记/自动连接）、驾驶与显示、首页布局、续航、RPM 加速、控制器历史和日志。

约束：

- 顶层 Tab 不超过 5 项，避免 iPhone 自动折叠为系统 `More`。
- 每个顶层 Tab 保持稳定位置和稳定标题，不按页面状态临时替换。
- 每个 Tab 由自己的 `NavigationStack` 管理子页面；返回必须使用系统返回手势和返回按钮。
- 不用自定义横向菜单、抽屉或手势覆盖系统返回手势。
- 不把“设置”复制到多个顶层入口；仪表盘可以提供续航结果的快捷入口，但设置只能从设置入口编辑。
- 导航标题使用简洁名词；页面内的动作放到 toolbar 或内容区，不把长句塞入标题。

### 2.2 页面分层

- **一级页面**：仪表盘、电池、控制器、行程、设置。
- **二级页面**：续航结果、续航设置、驾驶与显示设置、首页参数、蓝牙设备、控制器记录与历史、RPM 测试、日志、行程详情。
- **三级页面**：仅用于单条记录详情、参数选择或导出确认；如果内容可在一个页面内完成，不再增加层级。
- 需要确认的破坏性动作使用 `confirmationDialog` 或 `alert`，文案必须包含对象、影响和不可恢复性。

## 3. 视觉基础令牌

### 3.1 颜色

使用语义令牌，不在 Feature 页面散落原始颜色或直接写死 RGB/Hex。现有 `AppTheme` 是过渡入口，后续应逐步扩展为统一的语义颜色层。

| 语义 | SwiftUI 默认映射 | 使用规则 |
|---|---|---|
| `appBackground` | `Color(uiColor: .systemGroupedBackground)` | 页面背景，优先跟随系统明暗 |
| `surface` | `Color(uiColor: .secondarySystemGroupedBackground)` | 分组内容、非浮层卡片 |
| `elevatedSurface` | 系统标准 `Material` | 用于内容层中需要分离的表面；Liquid Glass 仅属于导航/控件层，不作为数据内容背景 |
| `primaryText` | `.primary` | 主标题和关键数值 |
| `secondaryText` | `.secondary` | 辅助说明、时间、来源和次级信息 |
| `accent` | `Color.accentColor` / 项目统一强调色 | 主要操作、选中状态、有效数据 |
| `success` | `.green` 的语义封装 | 连接正常、有效、完成；同时配文字或图标 |
| `warning` | `.orange` 的语义封装 | 过期、边界、待处理；同时配文字或图标 |
| `danger` | `.red` 的语义封装 | 断开、错误、删除和危险操作；同时配文字或图标 |
| `disabled` | `.tertiary` 或系统禁用样式 | 不可操作状态，不降低到无法识别 |

颜色规则：

- 浅色和深色模式都必须可读；主文本目标至少 4.5:1，对比度不足时不得通过降低字体大小补救。
- 状态至少由 **颜色 + SF Symbol/形状 + 文案** 中的两种表达。
- 禁止使用红绿两色作为唯一差异，尤其是电池状态、连接状态和曲线。
- 禁止页面内自行定义一套“更亮的蓝/绿/红”；新增语义色先补充到 `AppTheme`。
- 背景、边框和分隔线在两种主题下都必须可见；不依赖阴影表达唯一层级。

### 3.2 字体与数字

- 首选系统字体和 Dynamic Type：`.largeTitle`、`.title`、`.title2`、`.headline`、`.body`、`.callout`、`.subheadline`、`.footnote`、`.caption`。
- 禁止用 `.font(.system(size: ...))` 作为普通正文、标签或按钮的默认写法。
- 仪表盘关键数字可以使用系统 rounded/monospaced 设计，但必须使用可随 Dynamic Type 缩放的语义字体，并提供合理的换行或布局降级。
- 电压、电流、功率、RPM、速度、SOC 等数值统一使用 `.monospacedDigit()`，避免实时刷新导致字符跳动。
- 单位必须与数值形成清晰层级，不能依赖颜色区分单位；中文标题与英文单位之间保持统一空格规则。
- 不以 `lineLimit(1)` + 极小 `minimumScaleFactor` 解决所有溢出；优先重新布局、允许两行或缩短文案。
- 日志、UUID、协议十六进制内容可使用等宽字体，但必须限制在诊断页面，不扩散到普通用户界面。

### 3.3 间距、圆角与层级

采用 4/8 节奏，页面内只使用以下间距层级：

- `4pt`：图标与文字的紧凑间距。
- `8pt`：同一组件内的字段、卡片内行间距、网格间距。
- `12pt`：小分组之间或紧凑卡片内边距。
- `16pt`：标准页面水平内边距、标准 Section 间距。
- `20pt`：重点内容与容器的舒适间距。
- `24pt`：页面分区或 hero 状态区域。
- `32pt`：仅用于大型页面分段，不用于普通列表行。

约束：

- 新增间距优先补到 `Sources/DesignSystem` 的令牌，不在 Feature 中出现大量魔法数字。
- iOS 原生 `List`/`Form` 的行高、分组背景和系统内边距优先保留；不要为了“卡片化”重新包一层导致双重背景。
- 圆角最多使用三档：小型指标 `8pt`、普通容器 `12–16pt`、浮层/重点容器 `20pt`。不在同一层级混用多个任意圆角。
- 阴影只用于浮层或明显需要抬升的内容；普通分组优先依靠系统背景和分隔线。
- 不用缩放、位移或改变尺寸的按压效果造成周围布局抖动。

## 4. 常用组件 UI 库约束

组件应集中在 `Sources/DesignSystem`，Feature 页面只组合组件和提供业务数据。目标是形成小而稳定的内部 UI 库，而不是引入外部组件大包。

### 4.1 第一批公共组件

后续 UI 优化优先补齐以下组件；重要公共组件应有 Preview；关键交互需有 UI 测试或可重复的验证方式：

- `AppSectionHeader`：标题、辅助说明、可选操作入口。
- `AppMetricCard`：标题、值、单位、数据新鲜度和无效状态。
- `AppStatusBadge` / `AppConnectionStatus`：状态图标、状态文案、辅助说明。
- `AppEmptyState`：图标、标题、说明、主操作。
- `AppErrorState`：错误标题、可读原因、重试/导出日志操作。
- `AppLoadingState`：扫描、连接、读取、导出等操作的进度反馈。
- `AppSettingRow`：设置项标题、当前值、辅助说明、控件或导航箭头。
- `AppPrimaryAction` / `AppDestructiveAction`：统一按钮层级和禁用/加载状态。
- `AppChartContainer`：图表标题、时间范围、图例、空数据和 VoiceOver 摘要。
- `AppDeviceRow`：设备名、稳定 ID/RSSI、连接状态和可操作反馈。

### 4.2 组件行为

- 主操作使用原生 `Button`，次级跳转使用 `NavigationLink`；禁止用 `HStack.onTapGesture` 伪装按钮。
- 所有可点击区域至少 `44pt × 44pt`，图标按钮必须有 `.accessibilityLabel`；视觉图标尺寸可以小于 44pt，但命中区域不能小于 44pt。
- 相邻可点击元素至少保留 `8pt` 间距，避免误触。
- Button 的 pressed、disabled、loading 状态必须可见，但不能改变布局边界。
- 操作反馈在约 100ms 内可见；短交互使用系统动画，通常控制在 150–300ms；长任务使用明确进度或阶段文案。
- 所有组件必须支持 `.tint`、深色模式和系统字体；不得把文字颜色、背景色和业务状态绑死在组件内部。
- 组件的无障碍语义应在组件内部提供，业务页面只补充业务上下文。

### 4.3 表单、列表和确认

- 设置页面使用 `Form` + `Section`，读取型详情使用 `List` + `Section` + `LabeledContent`。
- 每个输入项必须有可见标题；placeholder 不能替代 label。
- 数值输入使用合适的键盘，单位显示在 label、`LabeledContent` 或辅助说明中，不让用户猜单位。
- 校验错误贴近对应字段，说明允许范围和修复方式；保存失败后保留输入，不静默覆盖。
- 保存/取消/恢复默认/清除窗口等行为的状态必须明确；恢复默认和清除数据需要确认。
- 大量数据使用 `LazyVStack`/`LazyVGrid` 或 `List`，避免普通 `VStack` 承载长列表。

## 5. 仪表盘与实时数据约束

### 5.1 信息层级

仪表盘按以下优先级组织：

1. BMS/控制器连接与数据新鲜度。
2. 速度、SOC/电压、功率等驾驶中需要快速扫读的关键值。
3. 行程开始/结束和当前行程摘要。
4. 续航结果及“为什么无结果”的原因。
5. 次级指标和曲线。

- 首屏不得同时放入所有诊断字段；次级数据下沉到详情、设备、控制器和日志页面。
- 关键状态卡必须同时显示状态文案和最近更新时间/新鲜度；仅显示一个彩色圆点不合格。
- “连接中”“已连接但数据过期”“未连接”“蓝牙关闭”“读取失败”必须是不同状态，不共用一个泛化错误文案。
- 关键数据不因为横竖屏切换而改变语义顺序；允许由单列切换为双列，但不允许出现横向滚动。

### 5.2 自适应布局

- 以可用宽度为依据，优先使用 `LazyVGrid`、`AnyLayout`、`ViewThatFits` 等 iOS 16 可用的 SwiftUI 布局工具；避免让一个 `GeometryReader` 包住整页后再用固定宽高拼装。
- 不用 `frame(width: 290)`、固定 `frame(height: 118)` 等值作为主要布局策略；若确需固定高度，必须证明在小屏、横屏和最大 Dynamic Type 下不裁剪。
- 最小验证宽度按 375pt 处理；同时验证大屏手机、横屏和系统文字放大。
- 图表与卡片必须保留可读的最小高度，数据不足时使用明确空状态，不绘制误导性曲线。
- 需要在驾驶时查看的内容避免过深滚动；设置和导出可以使用长滚动列表。

### 5.3 实时刷新与动效

- 每秒刷新不得触发整页重建或布局跳动；将实时值限制在对应组件的状态更新范围。
- 数字刷新可以使用 `.contentTransition` 或轻量过渡，但必须尊重 `accessibilityReduceMotion`。
- 不用闪烁、持续脉冲、无限旋转来表达“正常”；旋转只用于扫描/连接等进行中的任务。
- 过期状态优先静态标记和文字说明，不使用危险的强烈动效吸引注意。

## 6. 图表与数据可视化约束

- 有坐标、时间范围、筛选和可读性要求的业务图表优先使用 Swift Charts；`Canvas` 仅用于明确不需要交互的轻量绘制。
- 每个图表必须有标题、单位、时间范围或采样范围，并说明缺失值/断点如何处理。
- 不用颜色单独表达充电/放电、正常/异常；增加图例、符号、正负方向或文本摘要。
- 图表中的可交互点、按钮或时间范围选择至少满足 44pt 命中区域。
- VoiceOver 必须能得到图表的文字摘要；无法提供可访问图表时，提供同数据的列表/摘要替代。
- 图表空数据、数据不足、数据过期和数据断点必须分别处理；禁止把“等待数据”画成一条平线。

## 7. 无障碍与系统行为

交付任何页面前必须验证：

- Dynamic Type 至少覆盖默认大小和最大辅助功能字号；文本不被截断到失去语义，横屏也不溢出。
- VoiceOver 顺序与视觉顺序一致；按钮、导航入口、切换项、图表和状态都有有意义的 label/value/hint。
- 颜色对比在浅色/深色模式都可读；状态不依赖颜色单独传达。
- 支持减少动态效果；动效被关闭后功能和状态仍完整。
- 系统返回手势、键盘、分享面板和 sheet 下滑关闭不被阻塞。
- 表单焦点、键盘遮挡和输入错误可恢复；不要要求用户通过点击空白区域猜测如何收起键盘。
- 所有危险操作有清晰的取消路径；删除、清除、断开等动作不能通过误触直接完成。
- 权限、蓝牙关闭、定位不可用等系统前置条件要有可读的解释和下一步动作。

## 8. 页面级约束文件

当某页面有特殊布局要求时，在 `design-system/anturide-ios/pages/` 新增对应文件，例如：

- `dashboard.md`：驾驶仪表盘的首屏优先级、横竖屏布局和实时刷新例外。
- `settings.md`：设置分组、输入校验和危险操作。
- `trips.md`：行程列表、图表、导出和空状态。
- `diagnostics.md`：日志、控制器、BMS 详情的高密度数据展示。

页面级文件只能补充或收紧本主约束，不能降低 44pt 触控、Dynamic Type、VoiceOver、数据可信度或安全确认要求。

## 9. 当前代码基线与优先优化方向

当前仓库已经具备以下基础，不要在优化时回退：

- 顶层固定五项 Tab，避免系统 `More`。
- 页面基本使用 `NavigationStack`、`List`、`Form`、`Section`。
- 主题支持跟随系统/浅色/深色。
- 关键 UI 流程已有 `accessibilityIdentifier`，并有启动、空列表、行程、设置、横屏 UI 测试。
- 实时数据已有新鲜度和 `--` 缺失值语义；续航、行程、控制器、RPM 范围边界已有较多业务说明。

下一阶段默认按以下顺序优化：

1. 抽离统一的字体、间距、语义颜色和卡片/状态/空状态组件，减少 Feature 内重复样式。
2. 优先重构仪表盘固定字号和固定尺寸，确保 375pt、横屏和最大 Dynamic Type 不裁剪、不横向滚动。
3. 为 BMS/控制器状态、过期数据、续航不可用、扫描/连接/错误建立统一状态组件和可访问文案。
4. 为 Dashboard 的 Canvas 曲线补齐单位、时间范围、断点说明和 VoiceOver 文本摘要；评估迁移到 Swift Charts。
5. 优化设置页的分组、输入字段辅助说明、校验错误位置和保存/恢复默认反馈。
6. 为设备、行程、控制器历史、日志补齐加载/空/失败/重试状态和统一导出反馈。
7. 建立浅色/深色、Dynamic Type、减少动态效果、横竖屏的 UI 回归矩阵，并在 UI 测试中锁定关键状态。

## 10. UI 交付检查清单

### 视觉与布局

- [ ] 使用系统字体或 Dynamic Type 语义字体，没有普通文本的固定字号。
- [ ] 没有页面级原始颜色；颜色来自语义令牌。
- [ ] 间距符合 4/8 节奏，卡片、列表和 Section 层级一致。
- [ ] 375pt 小屏、横屏、大字号下不裁剪、不重叠、不横向滚动。
- [ ] 没有把 Liquid Glass/阴影/渐变当作所有内容的默认背景。

### 交互

- [ ] 所有动作使用语义控件，触控区域至少 44pt。

## 12. Dashboard 信息层级与 Swift Charts 补充约束（北京时间 2026-10-11 13:11:19 +08:00）

### 12.1 Dashboard 信息层级与入口

1. 用户配置的首页参数与驾驶关键数值优先，合理利用屏幕可用空间；“参数尽量填满首页”不要求把全部诊断字段挤入首屏。
2. 与参数直接相关的业务趋势图，其次是参数自身的数据有效性、新鲜度和不可用原因。
3. 续航结果等既有快捷入口可保留，但不能重新制造标题留白或扩展重复设置入口。

- 首页不显示“安途”标题，不保留标题造成的顶部空白。
- 首页不放独立 BMS 状态卡；设备 Tab 继续承载扫描/连接与状态管理。参数及其必要说明仍须区分未连接、有效、过期、缺失和错误，不能将移除状态卡解释为删除数据可信度提示。

### 12.2 导航栏区域全屏视觉与自适应

- Dashboard 滚动内容获得导航栏区域的全屏视觉，避免隐藏标题后仍保留大块顶部空白。全屏视觉不等于将所有内容/操作无条件越过安全区域，也不要求移除系统工具栏或导航能力。
- 内容与可操作控件不能被状态栏、灵动岛、导航控件或底部 Tab 遮挡；保留系统滚动与返回行为。
- 以可用宽度、自适应布局和语义字号安排参数密度；375pt 小屏、大屏、横竖屏及最大辅助功能字号均须可用，不用固定宽高、裁剪或缩小文字强行填满。
- 继续复用 `AppTheme.swift` 的语义主题；浅色/深色、Dynamic Type、VoiceOver、减少动态效果、44pt 触控和清晰反馈不得降低。

### 12.3 Dashboard Swift Charts 约束

- 继续遵守 iOS 16 最低版本；任何超出最低版本的图表 API 必须有明确版本保护与等价降级，不因图表迁移提高系统版本要求。
- 每图保留标题、单位、时间/采样范围和必要图例；正负方向及状态不只依赖颜色。
- 有效数据、数据不足、缺失、过期和时间断点分别处理；不造零值/平线，不跨缺口画出误导性的连续曲线。
- 提供 VoiceOver 可理解的文字摘要；图表交互不阻断页面滚动，交互控件保留至少 44pt 触控区域。
- 迁移不得改变既有采样来源、BMS 数据语义或本机隐私边界；RPM 加速继续为 RPM-only，不加入 GPS/IMU 融合。
